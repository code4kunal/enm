  1. GET /api/v1/openapi.json
  2. Look at EntryCreate.properties.data
EXPECTED: The register payloads are the heart of the contract. Five field lists,
          each mirroring a paper register, with required fields, master-backed
          dropdowns and numeric ranges.
ACTUAL:   {"type": "object", "title": "Data"}

          Nothing more. `WorkDoneData`, `CoolantData`, `DriverComplaintData`
          and `BreakdownData` do not appear in components/schemas at all.
TEST:     qa/api/test_field_validation.py (the whole module exists because of
          this — the expectations had to be sourced from HANDOFF instead)

Two consequences.

`tools/check_contract.py` verifies 298 Dart casts against the OpenAPI schema.
None of them can cover the register payloads, because the schema does not
describe them. The seam CLAUDE.md calls load-bearing is unchecked at exactly
the point where the five registers differ.

A new client has no way to learn the field lists except by reading
`app/schemas/entry.py` — which is the server's source, not its contract — or
by trial and error against a running API. This is how finding 0004 stayed
invisible: nothing published said what a breakdown's `data` contains.

STATUS:   CLOSED 2026-08-19. `app/openapi.py` generates the five payload
          schemas from the same models the API validates with — so they cannot
          drift from what it accepts — and points `EntryCreate.data` and
          `EntryUpdate.data` at a `oneOf` over them, with a description saying
          which `register` selects which.

          `BreakdownData` now publicly declares `route` and, since finding
          0004, no longer declares `resolved_at`. A test asserts that every
          field the contract publishes as required is a field the API actually
          enforces — a contract that says required on an API that accepts it
          missing is worse than no contract.
